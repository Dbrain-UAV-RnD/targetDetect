## 1. 오늘 바뀐 것과 그 이유

### 1.1 하드웨어 줌 → 디스플레이 줌
`ScalerCrop`을 센서 전체로 고정하고 줌을 출력 크롭으로만 처리.

**이유는 화질이 아니라 좌표계 안정성.** 예전엔 줌 도중 ScalerCrop이 계속 바뀌어 CAP 좌표계가 프레임마다 스케일됐고, 추적기·PTZ·속도추정을 매번 rebase해야 했다(반영에 7프레임 지연). 크롭을 고정하니 rebase 경로 4개를 전부 삭제했고, **줌 1.0→3.0 전 구간에서 추적 중심이 1px만 움직였다.**

부수 효과: CAP 좌표계가 줌과 무관하게 불변 → 비동기 결과에 `zoom_epoch` 같은 식별자가 불필요.

### 1.2 리샘플링
`warpAffine(INTER_LINEAR)` → `정수 크롭 + resize`. 축소는 `INTER_AREA`, 확대는 `INTER_CUBIC`.

INTER_LINEAR은 2x2 이웃만 봐서 3배 축소 시 화소 대부분을 버린다. 그 에일리어싱이 **고주파 에너지를 2배(254.7 vs 130.8)로 올려** H.264가 감당 못 하고 키프레임마다 블록이 튀었다.

### 1.3 RTSP 인코더 — intra-refresh
`cbr4000 ultrafast gop14` → `cbr2500 veryfast gop(2초) vbv300 intra-refresh`.

"1초 주기 모자이크"는 비트 부족이 아니었다(CRF20으로 뽑으면 1059kbps면 충분). **IDR 키프레임 버스트**가 원인 — 키프레임 하나가 RTP 패킷 87개로 몰려나가 수신측이 흘리면 다음 키프레임까지 깨진 채 유지된다. intra-refresh가 그 버스트를 없앤다.

Pi 쪽 송신은 무결함이 확인됨(로컬 수신 디코딩 오류 0, UDP/eth0 드롭 0). 증상이 남으면 **수신측** 문제다.

### 1.4 센서 모드 4608x2592@14 → 2304x1296@24
4608 모드는 상한이 14.35fps. 2304 모드는 **화각이 동일한데(둘 다 크롭 (0,0)/4608x2592) 56fps까지 가능**하고 2x2 비닝이라 노출·게인도 유리. 1536x864 모드는 화각이 좁아지므로 쓰면 안 된다.

30fps도 시도했으나 LightFC와 CPU를 다투다 오히려 fps 24.6으로 떨어져 24로 확정.

### 1.5 속도 추정 수정
리드 계산이 이동량을 **프레임 간격**으로 나눴는데 표적은 추적 갱신 주기로만 바뀐다. 갱신 없는 프레임에선 속도가 0으로 끌리고 갱신된 프레임에선 과대평가됐다. **표적이 실제로 바뀐 시각 기준**으로 바꿔서 갱신율과 무관하게 정확해졌다.

### 1.6 LightFC 템플릿 갱신 (미검증)
템플릿이 `_start`에서 한 번 뜨고 영구 고정이라 회전하면 점수가 떨어져 놓쳤다. 점수가 높을 때만 현재 모습을 조금씩 섞도록 추가. 추론할 때 어차피 `LFC_IN_Z`를 매번 넣으므로 **추가 추론 비용 없음.**

**실기 검증 안 됨.** 벤치에 회전 표적을 만들 수 없었다.

### 1.7 기타
- `LFC_MAX_MISS`가 갱신 "횟수"라 `LFC_RATE`를 바꾸면 타임아웃이 같이 변했다 → 시간 기준(`LFC_MISS_SEC=5.6`)으로 변경.
- 웹 미리보기 JPEG을 시청자 있을 때만 인코딩 (work_med 7.6ms 절약).
- `MAX_ZOOM` 5.0. 실화소 상한은 `REAL_ZOOM`(=CAP_W/OUT_W=1.8)이고 그 위는 보간. `/status`에 `zoom_max`/`zoom_real` 노출.
- CAP 픽셀 단위 상수(`PAN_STEP`, `FOLLOW_LEAD_MAX`, `LFC_INIT_BOX`)를 `CAP_K = CAP_W/1920`으로 스케일. **CAP 해상도를 바꾸면 이 상수들의 화각 의미가 달라지므로 반드시 함께 스케일돼야 한다.**
- `digital_gimbal_pc2.py`를 `digital_gimbal.py`로 통합, `pc2` 삭제. 두 파일 차이는 안정화(사용자 지시로 폐기)뿐이었다.
- `/etc/systemd/system/digital-gimbal.service.d/pc2.conf` 드롭인 제거(삭제된 파일을 가리켜 서비스가 죽었었다).

- **Compute Module 5.** `camera_auto_detect=1`이 동작하지 않는다(CM 계열은 검출 EEPROM 경로 없음). `config.txt`에 `dtoverlay=imx708,cam0` 명시 필수. 백업: `/boot/firmware/config.txt.bak-20260814`.
- 카메라 전원은 RP1 **GPIO34**(`CD0_IO0_MICCLK`)의 `cam0_reg`.
- Hailo-8은 재부팅으로 살아났다. 죽으면 `Device disconnected while opening device`.
- venv는 `/home/gimbal/.venv-gimbal` (시스템 python3에는 onnxruntime 없음).
- **i2c 노드 이름이 CSI 포트에 따라 갈린다** — `10-001a` / `11-001a`. 주소를 박아두지 말고
  `imx708` 로 잡힌 노드를 찾아 바인딩 여부만 볼 것. CM3 Wide 는 name 이 `imx708_wide` 지만
  드라이버 디렉터리는 동일하게 `imx708` 이다. (`gimbal-camera-ready.sh` 가 이렇게 동작한다)
- **서비스에 `CapabilityBoundingSet` 을 걸지 말 것.** RTSP 가 554(1024 미만)라 비루트
  프로세스에 `CAP_NET_BIND_SERVICE` 가 필요한데, BoundingSet 을 걸면 root 로 도는
  `ExecStartPre` 가 i2c/sysfs 를 못 만진다.
- **HailoRT 출력 포맷은 반드시 `FormatType.FLOAT32`** 로 지정한다. 기본값은 양자화된
  uint8/uint16 이고 그대로 쓰면 추적이 통째로 어긋난다. 입력도 마찬가지(§9).
- **렌즈가 `LensPosition 0.0`(무한대) 고정.** 실내 2m 물체는 선명도가 오토포커스 대비 1/19(8.2 vs 153.8)이라 **실내 벤치에서 추적기 성능 평가가 불가능하다.**

## 4. 열려 있는 결정 — 여기서부터 시작

### 최우선: 어떤 회전인가?
`estimateAffinePartial2D`는 **면내(in-plane) 회전만** 모델링한다.

- **면내**(화면에서 빙글) → FlowTracker 계획 유효
- **면외**(차량 선회, 기체 뱅크) → **계획 전체 무효.** 유사변환이 맞지 않고 특징점이 자기가림으로 사라진다. 이 경우 대책은 이미 넣은 템플릿 갱신 튜닝 + 재획득.

**이걸 확인하기 전엔 착수 근거가 없다.** 현재 우리가 가진 실기 데이터는 "회전에 약하다"는 관찰 한 줄뿐이고, 템플릿 갱신도 미검증이다.

### ~~즉시 가능 (10분)~~ → 2026-08-18 적용 완료
- ORT `allow_spinning=0` 적용. `ORT_SPINNING` env 로 되돌림 가능. **주의: §4 에 적혀 있던 "꼬리 765→153ms" 는 `threads=1` 행의 숫자였고 실행 설정은 `threads=2` 라 해당 없음** (§3 표 기준 153→125ms).

### 다음 실기에서 볼 것
- 회전 상황 기록 + `track_score`/`mode` 관찰
- 면내/면외 판정, 템플릿 갱신 효과, 실제 운용 지장 크기

### 그 후 (외부 리뷰 2건 반영한 순서)
0A CPU 구간별 계측·ORT/OpenCV 스레드 튜닝 → 0B LightFC head Hailo 이관(통과조건: 수치정확도, **score 임계값 재도출**, end-to-end p99, deadline 여유) → 1 FlowTracker shadow+텔레메트리+저부하 덤프 → 1.5 리플레이 + **희소 정답 라벨 + 홀드아웃** → 2A 시간정렬 shadow 융합 → 2B 제한적 제어연결 → 3 역회전.

**핵심 주의점:**
- 비동기 LightFC 결과는 **시간 정렬(Flow affine 누적으로 현재 시점 전진)** 후에만 융합. 블렌딩은 지연을 못 고치고 진폭만 줄인다.
- `zoom_epoch`은 불필요(§1.1). 대신 `track_generation`/`template_generation` 필요.
- LightFC의 w,h는 축정렬 AABB라 회전시 변한다 → **중심만 전진·보정**. 크기·각도는 Flow 전담(scale pumping 방지).
- Flow 무효 + 고신뢰 LightFC면 소프트 블렌딩 말고 **하드 재고정**.
- head 양자화 캘리브레이션은 이미지가 아니라 **백본 feature 텐서**로.
- 리플레이는 재현성만 주고 정답성은 못 준다 → fiducial 등 정답 필요. 폐루프는 리플레이로 검증 불가 → 실기 shadow 필수.

## 6. 외부 리뷰 반영 — 설계 요구사항

FlowTracker + LightFC 융합 계획에 대해 외부 리뷰 2건을 받았다. 아래는 그 기술적
요구사항을 정리한 것이고, **각 항목의 채택 여부와 근거**를 함께 적었다.
출처: `[R1]` 1차 리뷰, `[R2]` 2차 리뷰, `[본인]` 이쪽 분석.

### 6.1 비동기 시간 정렬 — 최우선 요구사항 `[R1]` 채택

**블렌딩은 지연을 해결하지 못하고 진폭만 줄인다.** LightFC가 프레임 `k`를 처리한
결과를 프레임 `n`에서 반환하면 두 박스는 서로 다른 시점이다. 먼저 전진시켜야 한다.

```
B_lfc_now = A[n-1] · ... · A[k+1] · A[k] · B_lfc_k
```

크기 감각: 추론 40ms + 24fps → 1~2프레임 묵음. 표적이 프레임당 15px면
**박스(108px)의 14~28%가 어긋난 채로 섞인다.** 무시할 수준이 아니다.

재료는 공짜다 — FlowTracker가 내놓는 프레임간 affine이 곧 전진에 필요한 값이다.
최근 100~200ms 분을 링 버퍼로 유지. 버퍼 길이는 nominal 50ms가 아니라
**실제 완료 지연 최대치 + jitter 여유** 기준으로 잡을 것.

전진 실패 조건 (억지로 블렌딩하지 말고 재획득 후보로):
```
경로에 invalid transform 이 하나라도 있음
경로 최소 quality 가 임계값 미만
결과 age 가 LFC_MAX_RESULT_AGE_MS 초과
현재 Flow 와 거리가 과도
```

### 6.2 결과 메타데이터 `[R1][R2]` 채택 (zoom_epoch 제외)

```python
LightFCResult(
    source_frame_id, capture_timestamp, completion_timestamp,
    track_generation, template_generation, template_angle_at_submit,
    center, box, score,
)
FlowTransform(from_frame_id, to_frame_id, affine_3x3, valid, quality)
```

- **`zoom_epoch` 은 넣지 않는다** `[본인]`. 디스플레이 줌으로 CAP 좌표계가 줌과
  무관하게 불변이므로(§1.1), 줌 변경을 이유로 결과를 폐기하면 정상 측정을 버린다.
  리뷰는 줌이 좌표계를 바꾸는 시스템을 전제했는데 우리는 그 구조를 없앴다.
- **`track_generation` 은 필요하다** `[R2]`. 새 표적 클릭 후 이전 표적의 125ms 묵은
  결과가 도착할 수 있다. 좌표계가 같아도 대상 정체가 다르면 무효다.
- **`template_generation` / `template_angle_at_submit`** — 템플릿 갱신이 있으므로
  어느 템플릿으로 실행된 결과인지 알아야 한다. 3단계 역회전에서 특히 중요.

### 6.3 좌표 처리 `[R1]` 채택

- LK 의 `prevPts` 는 **이전 영상 좌표계**여야 한다. 현재 ROI 로 보정한 점을 넘기면
  안 된다. 초기 추정은 `OPTFLOW_USE_INITIAL_FLOW` 로 준다.
  (실제로 이 버그로 벤치의 이동 케이스가 전부 깨졌었다.)
- RANSAC 에는 **CAP 좌표로 변환한 점**을 넣는다.
- 고정 크기 패치(예: 256x256) + 명시적 `CAP↔patch` 행렬 보관이 origin 덧셈보다 깔끔.
- **`dx,dy` 를 affine 의 `tx,ty` 로 해석하면 안 된다.** 회전이 있으면 평행이동 항은
  중심 이동량과 다르다. 중심에 행렬을 적용해서 구할 것.
  `update()` 는 델타가 아니라 갱신된 박스 + affine 전체를 반환.

### 6.4 Flow 유효성 판정 `[R1][R2]` 채택

인라이어 개수만으로는 부족하다. 8개가 한쪽에 몰려 있으면 회전·배율 추정이 불안정.

```
n_inliers, inlier_ratio, forward-backward error,
RANSAC reprojection error, 인라이어 공간 분포(coverage),
프레임간 변환의 물리적 허용 범위
```

- `coverage` = 인라이어 convex hull 면적 / 박스 면적, 또는 3x3~4x4 격자 점유 셀 수.
- 특징점은 상위 N개가 아니라 **격자별 제한**으로 고르게 분포시킬 것(회전 추정에 유리).
- 마스크는 박스보다 약간 축소해서 배경 오염을 줄이고, 부족하면 원래 박스로 2차 검출.
- 물리 범위는 프레임당 고정값이 아니라 **실제 dt 기준**: `max_speed_px_s * dt`.
  CPU 포화로 프레임이 누락되면 고정 임계값은 무효가 된다 `[R2]`.

**가장 중요한 지표는 false-valid rate** `[R1]`. 제어에서는 "틀렸는데 valid"가
"맞는데 invalid"보다 훨씬 위험하다. 초기 임계값은 보수적으로.

FB 검증은 전부/전무 사이 절충이 있다 `[R2]`:
```
매 프레임    forward LK, RANSAC, ratio, reproj, coverage, 물리범위
격프레임     공간적으로 고른 인라이어 16~24개만 backward LK
의심 프레임  전체 FB + 특징점 재검출
```
실측 비용: 전체 FB+coverage 추가시 med +0.49ms, **p99 +2.69ms**. med 는 감당되나
p99 가 이미 튀는 프레임에 겹친다. 1.5단계 데이터로 정책 결정.

### 6.5 융합 우선순위 `[R1]` 채택

| 상태 | 동작 |
|---|---|
| Flow 유효 + 시간보정 LFC 일치 | 소프트 보정 |
| Flow 유효 + LFC 크게 불일치 | 게이팅, 섞지 않음 |
| Flow 무효 + LFC 신선·고신뢰 | **하드 재고정** |
| Flow 무효 + LFC 오래됨/저신뢰 | 기존 miss/fallback |
| 반복 불일치 | 재획득 모드 |

**Flow 무효인데 0.3만 이동하면 잘못된 상태를 오래 끌고 간다.** 하드 스냅이
위험했던 원인이 지연이었으므로, 시간 정렬(6.1)이 들어가면 하드 재고정이 맞다.

가중치는 분리한다:
```
중심 위치  LightFC 로 보정        (FLOW_ANCHOR_POS_W)
크기      Flow 담당 (초기엔 보정 안 함)
각도      Flow 담당, LightFC 로 보정하지 않음
```

**scale pumping 주의** `[R1]`: LightFC 는 축정렬 AABB 를 반환하므로 표적이 회전하면
실제 크기가 그대로여도 `w,h` 가 변한다. 그걸 회전 박스 고유 크기에 섞으면 회전
주기에 맞춰 박스가 커졌다 작아진다. 현재 `LFC_SIZE_ALPHA=0.0` 이라 자연스럽게 맞다.

`[R2]` 더 간단한 방법: **중심만 전진·비교하고 LightFC 의 `w,h` 는 텔레메트리로만
남긴다.** AABB 회전 의미 문제와 scale pumping 이 동시에 사라진다. 이쪽 채택.

### 6.6 특징점 재검출 정책 `[R1]` 채택

20Hz LFC + 24fps 에서 매 LFC 결과마다 reseed 하면 거의 매 프레임 reseed 가 된다.
아래 조건에서만:
```
앵커 보정량이 박스 대각선의 일정 비율 초과
인라이어 수 또는 coverage 저하
현재 특징점 수 임계값 미만
Flow 가 무효였다가 복구
```
**reseed 해도 누적 각도를 0으로 초기화하면 안 된다.** feature epoch 상대각과 템플릿
기준 절대각을 분리하거나, 누적 3x3 행렬을 유지하고 기준 행렬만 교체.

### 6.7 LightFC 의 성격 재정의 `[R1]` 채택

"절대 위치 추적기"라는 내 표현은 틀렸다. LightFC 는 이전 state 주변을
`search_factor` 만큼 크롭해 템플릿과 대조하는 **로컬 추적기**이지 전체 화면
검출기가 아니다. 정확한 표현:

> 저속이지만 누적 오차가 없는 외형 기반 **로컬** 측정값

따라서 Flow 가 크게 이탈하면 LightFC 탐색 패치도 잘못된 곳에서 생성되어
**둘 다 복구 실패**할 수 있다. 진짜 복구에는 별도 `REACQUIRE` 상태 필요:
```
정상        기본 search_factor
Flow 무효   search_factor 단계적 확대
여전히 실패 저주기 전체화면 검출기
```
전체화면 검출기 자산은 이미 있다 — `HailoDetector`(YOLOv8)가 `USE_DETECTOR=False`
로 꺼져 있다 `[본인]`.

임계값도 둘로 나눈다: `LFC_ACCEPT_SCORE`(소프트 보정) / `LFC_REACQUIRE_SCORE`(하드
재고정, 더 높게 — 잘못된 대상으로 점프 방지).

### 6.8 3단계 역회전 — `_crop(angle)` 만으로 끝나지 않음 `[R1]` 채택

LightFC 의 `map_box_back()` 은 **검색 패치가 회전되지 않고 축정렬로 잘렸다는 가정**을
쓴다. 패치를 회전시키면 그 공식을 그대로 쓸 수 없다.

함께 바뀌어야 할 것:
```
1. CAP → search patch 변환 행렬 생성 (crop 후 warp 가 아니라 한 번에)
2. 그 행렬로 패치 추출
3. LightFC 출력 patch 좌표를 역행렬로 CAP 복원
4. w,h 는 회전 박스 표현으로 보존
5. 화면용 축정렬 AABB 는 필요할 때만 계산
```

템플릿 기준각도 함께: `relative_angle = current_target_angle - template_angle`.
가장 깔끔한 건 **초기·갱신 템플릿과 검색 패치를 모두 정립(canonical) 방향으로 생성**.

**한계** `[R1]`: Flow 각도에는 절대 관측이 없다. LightFC 는 회전각을 측정하지 않는다.
따라서 역회전은 LightFC 의 회전 민감도를 줄일 뿐 **Flow 각도의 장기 드리프트는
고치지 못한다.** "회전을 근본 해결"이라던 표현은 과했다. 정확히는:

> 신뢰할 수 있는 Flow 각도가 있을 때 LightFC 입력의 면내 회전을 정규화한다

각도 품질이 낮은데 계속 역회전하면 오히려 입력이 흔들린다. 게이트 필요.

### 6.9 상태 머신 `[R1]` 채택

```
FLOW_FUSED / LFC_ONLY / LEGACY_FALLBACK / REACQUIRE / LOST
```
**한 시점에 하나의 모드만 제어 출력을 소유**한다. 모드 전환 시 넘겨받는 쪽을
현재 승인된 박스와 frame_id 로 재초기화할 것.

### 6.10 프레임 덤프 `[R2]` 채택

현재 시스템이 포화라 **덤프가 측정 대상을 바꿀 수 있다.**
```
capture thread → 사전할당 링버퍼
dump writer thread → 여유 있을 때 저장
저장 지연 시 → capture 를 막지 말고 dump frame drop + drop_count 기록
```
연속 저장보다 **이벤트 기반 pre-roll/post-roll**(최근 몇 초를 링버퍼에 유지, 트리거
발생 시 앞뒤만 저장).

**손실 압축(H.264) 저장 금지** — 블록 아티팩트와 ringing 이 코너·gradient 에 영향을
주어 실제 CAP 원본과 다른 LK 특성을 만든다. native 포맷 그대로 저장.
(참고: CAP gray = 3MB/frame, 24fps 5초 = 360MB. RAM 16GB 라 여유 있음.)

기록할 메타데이터: frame_id, monotonic timestamp, **실제 dt**, frame drop 여부,
승인 box, Flow points/inliers/affine, valid/reject reason, FB·reproj error, coverage,
LFC source_frame_id/submit·completion timestamp/score/box, track_generation,
template_generation, template_angle_at_submit, 현재 모드, 설정 전체, 빌드 식별자.

### 6.11 검증 — 리플레이만으로는 부족 `[R2]` 채택, 가장 중요

**재생은 재현성을 주지만 정답성을 주지 않는다.** 같은 실패를 반복 재현할 뿐
"Flow 가 옳았는가"는 답하지 못한다. LightFC 를 정답으로 쓸 수도 없다 — 그것도
회전에 약한 지연된 로컬 추적기다.

→ **희소 정답 데이터가 필요하다.** 전체 라벨링 불필요, 대표 구간만:
```
실제 중심, 회전각, 고유 폭/높이(또는 oriented box), 가림/블러/이탈 상태
```
실용적 방법: 표적에 **강체로 연결된 fiducial marker 를 특징점 마스크 바깥에** 배치.
추적기를 쉽게 만들지 않으면서 중심·각도 기준을 얻는다.

평가 지표:
```
center_error / box_diagonal,  wrapped_angle_error,
false-valid rate,  false-invalid rate,  recovery latency,  누적 drift
```
임계값은 평균 오차 최소가 아니라 **PTZ 제어가 허용할 수 있는 false-valid 수준**으로.
튜닝용 / 홀드아웃 / 최종 실기 기록을 분리할 것 (동일 영상으로 튜닝+평가하면 과적합).

**리플레이 시 비동기 지연도 재생해야 한다.** LightFC 를 프레임마다 즉시 실행하면
가장 중요한 시간 정렬 문제를 검증하지 못한다. 이벤트 기반으로:
```
FRAME / LFC_SUBMIT / LFC_COMPLETE / FLOW_UPDATE / FUSION
```
기록된 `completion_timestamp` 를 쓰거나 측정된 지연 분포를 주입.
125ms 는 약 3프레임이고 추론 주기 50ms 보다 길어 **FIFO 큐면 적체된다.**
실행·재생 모두 **깊이 1 mailbox 덮어쓰기**여야 한다.
(현재 코드는 이미 `self.pending = bgr` 로 덮어쓴다 — 이 요구는 충족 `[본인]`.)

### 6.12 폐루프는 리플레이로 검증 불가 → 2A shadow `[R2]` 채택

녹화 영상에서 제어 명령을 바꿔도 이후 프레임은 바뀌지 않는다. 따라서:

- **2A** 시간정렬 융합을 **shadow 로만** 실행. 실제 제어는 기존 경로.
  기록: 기존 제어 중심, shadow 융합 중심, raw/보정 flow_dist, would-be PTZ command,
  LFC age, anchor/reject 사유.
  확인: 보정 후 flow_dist 분포가 실제로 줄어드는가, 125ms spike 결과가 정상 전진 또는
  폐기되는가, 이전 generation 결과가 적용되지 않는가, anchor 가 왕복 진동을 만들지 않는가.
- **2B** 제한적 제어 연결. 명령 최대 변화량 제한, 기존 fallback 즉시 복귀,
  원클릭 롤백.

스위치 분리: `FLOW_ENABLE` / `FLOW_FUSION_ENABLE` / `FLOW_CONTROL_ENABLE` / `FLOW_DUMP_ENABLE`.

### 6.13 0단계 통과 조건 `[R2]` 채택

"Hailo 에서 실행됐다"가 아니라 넷 다 통과해야 완료:
```
1. 수치 정확도    — tensor 평균오차가 아니라 최종 출력 기준
                    center_error/box_diagonal, score 차이, score 순위 상관성,
                    LFC_SCORE_MIN 통과 여부가 바뀐 비율, 재획득 성공/실패 변화
2. score 임계값 안정성 — 양자화 후 score 분포가 달라진다.
                    **LFC_SCORE_MIN=0.60 유지를 전제하면 안 된다.** 1.5단계에서 재도출.
3. end-to-end p99 — host tensor 준비, quantize/format 변환, host→Hailo 전송,
                    inference, 출력 전송, dequantize, 후처리, 큐 전달 전부 포함.
                    Hailo profiler 의 모델 단독 추정치로 판단 금지.
                    작은 head 는 연산보다 전송·런타임 호출 비용이 클 수 있다.
                    persistent binding/buffer 사용(매 추론마다 buffer 생성 금지).
4. 실제 deadline 여유 — 앱 전체 경로에서 측정
```

**캘리브레이션 데이터는 head 입력 도메인이어야 한다** — 원본 프레임이 아니라
백본 feature tensor. 실측 확인: head 입력은 `[1,96,8,8]` + `[1,96,16,16]`.
기존 CPU 경로에 덤프를 추가해 template/search feature tensor, CPU head 출력,
최종 center/score 를 모으면 **양자화 캘리브레이션과 golden comparison 에 동시 사용** 가능.

### 6.14 0A 실측 결과 — 리뷰 기대와 어긋난 부분 `[본인]`

리뷰는 0A(스레드/spinning 튜닝)를 0B 앞에 두라고 했고, 이쪽은 "0A 로 충분하면
Hailo 불필요"를 기대했다. **실측 결과 그 기대는 틀렸다.** (수치는 §3 참조)

- spinning 은 중앙값이 아니라 **꼬리에 든다** (threads=1 max 765→153ms).
  `allow_spinning=0` 은 공짜 개선이므로 지금 넣을 것. **미적용 상태.**
- 그러나 head 는 경합 없이도 threads=2 에서 22ms. 20Hz 면 코어 44%, 경합시 1.3코어.
  **스레드 설정으로 해결될 규모가 아니다. 0B 는 필요하다.**

### 6.15 두 리뷰가 모두 놓친 것 `[본인]` — 착수 전 필수

**어떤 종류의 회전인지 모른다.** `estimateAffinePartial2D` 는 유사변환이므로
**면내 회전만** 표현한다.

```
면내  표적이 화면에서 빙글           → affine 모델링 가능
면외  차량 선회, 기체 뱅크, 표적 돌아섬 → 투영 형상이 비강체로 변함, 자기가림
```

**면외면 위 계획 전체가 헛일이다.** 8단계를 다 만들고도 아무것도 못 얻는다.
그리고 면외라면 유효한 대책은 **이미 넣어둔 템플릿 갱신**(외형 변화 추종)이다.

또한 정답 라벨링 시 **면내/면외를 구분해서 기록**해야 한다. 3D 물체의 면외 회전은
단일 각도로 정의되지 않는다.

### 6.16 규모에 대한 판단 `[본인]`

두 리뷰를 합치면 8단계 프로그램이다 — Hailo 변환·커스텀 캘리브레이션·정확도 게이트,
정답 라벨링, 홀드아웃 데이터셋, 이벤트 기반 리플레이 하네스, 상태 머신, shadow 융합.
**수 주 규모.**

그런데 현재 실기 데이터는 "회전에 약하다"는 관찰 한 줄뿐이다. 얼마나 자주, 어떤
각속도에서, 운용에 실제로 얼마나 지장인지 수치가 없다. 오늘 넣은 템플릿 갱신도 미검증.

**측정하지 않은 문제에 정교한 해법을 설계하고 있다.** 설계 품질 문제가 아니라
착수 순서 문제다. §4 의 판단 순서를 따를 것.

## 7. 0A 계측 결과 (2026-08-18) — 0B 착수 근거 확보

§6.14 가 "0A 로 충분하지 않다"까지만 말했고 **103ms 의 내역은 아무도 재보지 않았다.**
`_update` 에 `perf_counter` 4구간을 넣어 실측했다. `/status` 의 `lfc_stage` 로 상시 노출된다.

측정 조건: 24fps, zoom 1.0(최악), RTSP 클라이언트 1, 웹 시청자 0,
중앙 108px 박스, 타임아웃 회피 위해 4초마다 재클릭, 각 200 사이클.

### 구간별 (med / p95, ms)

| 구간 | 기본(cv=4) | cv=2 | 최종(cv=2 재확인) |
|---|---|---|---|
| crop (검색패치+cvtColor) | 1.57 / 4.42 | 1.51 / 2.64 | — |
| **Hailo backbone infer** | **3.48** / 10.87 | **3.79** / 11.23 | **3.42** / 10.08 |
| transpose NHWC→NCHW | 0.16 / 0.72 | 0.15 / 0.60 | — |
| **CPU ONNX head** | **55.63** / 95.47 | **53.53** / 89.19 | **48.94** / 93.15 |
| 4구간 합 (med) | 60.84 | 58.98 | — |
| 사이클 전체 (med/p95) | 64.64 / 111.53 | 60.26 / 99.16 | 56.52 / 102.81 |
| 실효 갱신율 | 15.47 Hz | 16.59 Hz | 17.69 Hz |

### 결론

**head 가 전체의 86~91% 다.** Hailo backbone 은 3.5ms 로 사실상 공짜고,
transpose(0.16ms)는 신경 쓸 가치가 없다. 후처리는 사이클 합과 4구간 합의 차이인 약 3.8ms.

→ **0B(head Hailo 이관)는 근거가 확보됐다.** head 를 걷어내면 사이클이 60ms → 10ms 대가 되어
`LFC_RATE=20` 설정값에 여유롭게 도달하고 CPU 1.5코어가 풀린다.
§6.13 의 통과조건 4개는 그대로 유효하다.

### 정정

- **`/status` 의 `ms` 필드는 마지막 1회 샘플이다** (중앙값 아님). 이전에 관측된 `ms=103.3`
  을 대표값으로 읽고 "실효 9.68Hz" 라고 판단했으나, 실제 중앙값은 60ms 대이고
  103ms 는 p95(99~111ms) 부근의 꼬리 샘플이었다.
- 따라서 아래 타임아웃 버그의 크기도 11.6초가 아니라 **약 7.2초**였다(의도 5.6초).

### 함께 고친 것

- **LFC 타임아웃 버그.** `LFC_MAX_MISS = round(LFC_RATE * LFC_MISS_SEC)` 가 **설정된** 20Hz 로
  환산했는데 실효 갱신율은 15~17Hz 라 실제 타임아웃이 5.6초가 아닌 약 7.2초였다.
  §1.7 이 시간 기준으로 고쳤던 문제가 "실효 레이트가 설정값을 못 따라간다"는 형태로 되살아난 것.
  → `miss_t0` 벽시계 기준으로 변경. `LFC_MAX_MISS` 상수 삭제.
- `_loop` 의 `sleep(max(0, 1/LFC_RATE - el))` 은 `el > 50ms` 라 **항상 0** 이다.
  LFC 스레드는 쉬지 않고 돈다. 느려서 CPU 를 더 먹고 CPU 를 먹어서 더 느려지는 구조.
  0B 로 사이클이 짧아지면 자연히 해소된다.
- `CV_THREADS` 기본 2. 4코어 포화 상태에서 OpenCV 4스레드가 x264·LFC 와 경합했다.
  사이클 p95 111.5→99.2ms, 갱신율 +7%. **단회 측정이고 폭이 작다** — 저전압 이력(§0)을
  감안하면 노이즈 범위일 수 있으나 4개 지표가 같은 방향이라 채택. `CV_THREADS=4` 로 되돌림 가능.

## 8. 지연 예측 적용 + 0B 준비 (2026-08-18)

### 8.1 갱신 사이 예측 — 적용 완료

문제: LFC 갱신이 17.7Hz 인데 화면은 24fps 라 **4프레임 중 1프레임은 박스가 얼어붙는다.**
게다가 §6.1 대로 결과가 56ms(p95 103ms) 묵었는데 보정이 전혀 없었다.

FlowTracker 없이 가능한 1차 근사를 넣었다. **재료는 이미 있었다** — 속도 추정 `tvx,tvy`.

```
LightFCResult 에 t_result (결과 생성 시각) 추가
age       = clamp(now - t_result, 0, PRED_MAX_AGE=0.15)
pred_dx   = clamp(tvx * age, ±FOLLOW_LEAD_MAX)
제어 목표  = 중심 + pred + (tvx * LEAD_TIME)      ← 기존 리드는 유지
표시 박스  = 중심 + pred                          ← 매 프레임 이동
```

**속도 추정의 시간 기준도 함께 고쳤다.** §1.5 가 "표적이 실제로 바뀐 시각"으로 바꿨지만
그건 *변화를 관찰한 프레임* 시각이었다. 이제 *측정이 생성된* `t_result` 를 쓴다.
프레임 경계만큼(최대 41.7ms) 더 정확하다.

검증: v=10.8px/s, age=150ms → dx=1.62 (보고값 1.6). 정상 동작.
`PRED_ENABLE=0` 으로 끌 수 있고 `/status` 의 `pred` 로 age/dx/dy/vx/vy 가 상시 노출된다.

**주의**: score < `LFC_SCORE_MIN` 인 동안은 `t_result` 가 멈춰 age 가 상한(150ms)에 붙는다.
박스가 `v*0.15` 만큼 고정 오프셋을 갖지만 발산하지는 않는다.
**실기 표적으로 shadow 검증 전에는 제어 개선을 단정하지 말 것** (§6.5).

### 8.2 0B 준비 — head 분할 지점 확정

**DFC(`hailo_sdk_client`)는 x86 전용이고 Pi 에는 런타임(HailoRT 4.23)만 있다.**
컴파일에는 x86 리눅스 PC 가 필요하다. Pi 에서만 가능한 준비를 마쳤다.

#### 수집한 데이터 — `/home/gimbal/lfc_calib` (256 샘플, 23MB)

§6.13 이 요구한 대로 **head 입력 도메인(백본 feature tensor)** 이다. 원본 이미지가 아니다.

```
fz     [1,96,8,8]    float32   범위 -3.44 ~  3.17,  mean 0.005, std 0.459
fx     [1,96,16,16]  float32   범위 -3.80 ~  3.62,  mean-0.005, std 0.420
score  [1,1,16,16]   ┐
size   [1,2,16,16]   ├ CPU head 골든 출력 (수치정확도 비교용)
offset [1,2,16,16]   ┘
box, rf                        후처리 재현용
```

**한계**: score peak 가 0.207~0.927, 평균 0.443 이고 **`>=0.60` 은 256 중 40 개뿐이다.**
실내 렌즈 무한대 고정(§2) 때문이다. 캘리브레이션 입력 분포로는 충분하나,
**§6.13 요구조건 2(score 임계값 재도출)는 이 데이터로 못 한다 — 실기 기록이 필요하다.**

#### Hailo 위험 연산 두 개 — 그리고 그게 문제가 안 되는 이유

백본만 HEF 로 컴파일돼 있고 head 는 안 된 이유가 여기 있을 것으로 보인다:

```
#2~#7  Reshape→Transpose→Reshape→MatMul→Reshape   ← 상관연산(ECM).
                                                     활성×활성 MatMul 은 데이터플로우에 불리
#20~21 Conv→Div→Erf→Add                           ← GELU. Erf 지원 여부가 DFC 버전에 달림

**그런데 둘을 합쳐 0.49ms, 전체의 0.9% 다.** 그리고 **둘 다 그래프 앞쪽에 몰려 있다.**

실행 순서 기준 분할 비용:

| 분할 지점 | CPU 잔류 | Hailo 이관 |
|---|---|---|
| MatMul 직후 (실행순 2) | 0.26 ms (0.6%) | 42.94 ms (**99.4%**) |
| **Gelu 직후 (실행순 11)** | **0.92 ms (2.1%)** | **42.28 ms (97.9%)** |

→ **Gelu 출력에서 한 번만 자르면 위험 연산 두 개가 모두 CPU 쪽에 남고,
컨볼루션 덩어리 97.9% 가 통째로 Hailo 로 간다.** 그래프 중간을 왕복할 필요가 없다.

분할·수치검증·캘리브레이션 생성까지 Pi 에서 끝냈다. **PC 에서는 컴파일만 하면 된다.**

## 9. 0B 완료 (2026-08-18) — head 를 Hailo 로 이관

x86 PC 에서 `A_back.onnx` 컴파일 성공. 컴파일 측 상세는 `1CH/HAILO_0B_RESULT.md`.

### 결과

| 구간 (med/ms) | 이전 | 통합 후 |
|---|---|---|
| crop | 1.57 | 1.76 |
| backbone | 3.42 | **9.47** ← 컨텍스트 전환 +6.05 |
| transpose | 0.16 | 0.14 |
| head | **48.94** | **9.51** ← front(CPU) + head_back(Hailo) |
| **연산 합계** | **58.98** | **20.88** |
| 사이클 | 56.52 | 41.77 (p95 45.51) |
| **실효 갱신율** | **17.69 Hz** | **23.94 Hz** |
| CPU idle | 14~22% | **43.8%** |

**`LFC_RATE` 기본값을 `FPS`(24) 로 바꿨다.** 연산이 20.9ms 뿐이라 사이클 41.77ms 는
compute 가 아니라 `sleep` 이 정한다. **LFC 스레드가 처음으로 잠든다** — §7 이 지적한
"느려서 CPU 를 더 먹고 CPU 를 먹어서 더 느려지는" 구조가 해소됐다.

### 컨텍스트 전환 — 예상 못 한 비용

백본과 head_back 이 **별도 HEF = 별도 네트워크 그룹**이라 교대 실행 시 전환이 일어난다.
실측으로 분리했다:

```
① activate() 방식, 백본만          2.59 ms
② 스케줄러, 백본만                  2.62 ms   ← 스케줄러 자체 오버헤드는 0.03ms
③ 스케줄러, head_back 도 구성만      2.62 ms   ← 구성만으로는 안 느려짐
④ 실제 교대 실행                    9.47 ms   ← 여기서 발생. 사이클당 2회 전환 ≈ 12ms
```

없앨 방법은 **둘을 하나의 HEF 로 합쳐 단일 컨텍스트에 올리는 것**뿐인데, 사이에
CPU 상관연산이 끼어 있어 현재 구조로는 불가능하다. 지금도 24Hz 여유가 충분하므로
추가 작업 근거는 없다. 더 필요해지면 그때 검토.

### 앱 변경

```
LFC_HEAD_FRONT = models/split/A_front.onnx     상관연산(활성×활성 MatMul). CPU 잔류
LFC_HEAD_HEF   = models/lightfc_head_back.hef  나머지 97.9%. Hailo
LFC_HEAD_HAILO = 1                             0 이면 기존 CPU head 로 복귀
```

- VDevice 를 `HailoSchedulingAlgorithm.ROUND_ROBIN` 으로 생성. **스케줄러 모드에서는
  `ng.activate()` 를 호출하면 안 된다** — 기존 경로는 `LFC_HEAD_HAILO=0` 일 때만 activate.
- 입출력 모두 `FormatType.FLOAT32`. 기본값은 양자화 uint8/uint16 이라 그대로 쓰면 어긋난다.
- head_back 입력은 **NHWC**. 채널 수로 구분한다 (64 = 상관출력, 96 = 원본 fx).

### ⚠ 출력 이름 함정 — 두 번 당했다

`HAILO_0B_RESULT.md` §8 은 출력 vstream 이 `output_layer1/2/3` 이라고 적었으나
**실물은 `activation1` / `activation2` / `conv14`** 다. 게다가 `size_map` 과
`offset_map` 은 둘 다 `(16,16,2)` 라 shape 로 구분되지 않는다.

→ 이름·순서에 의존하지 않고 **값 범위로 자동 판정**하도록 `_map_outputs()` 를 넣었다.

```
1채널            → score_map
2채널, min >= 0  → size_map    (Sigmoid→Clip 이라 [0,1])
2채널, 음수 포함  → offset_map  (Conv 원출력)
```

재컴파일로 이름이 또 바뀌어도 동작한다. `validate_0b.py` 도 같은 방식으로 고쳤다.

## 10. 거리변화 추적 · ROI 안정화 · YOLO 제거 (2026-08-21)

### 10.1 YOLO 제거
`USE_DETECTOR` 가 이미 `False` 였으므로 런타임 변화 없음. `HailoDetector`,
`DetectionTracker`, `iou()`, `DET_*`, `HEF_PATHS` 삭제. GCS `CMD_AI_MODE`(show_det)
는 프로토콜 호환 위해 파싱만 남겼고 **아무 동작도 하지 않는다.**

### 10.2 ROI 흔들림 — 표시 박스에 lag 데드밴드
`_crop` 이 crop 원점을 `int(round())` 로 양자화하고 그 결과가 다음 프레임 crop 위치로
되먹임돼, 정지 장면에서도 박스가 랜덤워크한다.

`LightFCTracker._stab()` 추가. **스텝이 아니라 raw 박스와 표시 박스의 누적 거리**에
데드밴드를 건다 → 정지 시 완전히 굳고, 느린 드리프트도 결국 따라가며(정상상태 지연
= 데드밴드), 급기동(d ≥ SPAN)에서는 게인 1.0 이라 지연이 없다. 추적 내부 crop 은
**raw 박스**를 그대로 쓴다(추적 성능 불변). `snapshot()` 만 안정화 박스를 내보내므로
표시·PTZ 타깃·속도추정(`tvx/tvy`)·`pred_dx/dy` 가 모두 함께 조용해진다.

실측(락 상태, 20초, 상태파일 샘플 292): 박스 갱신 횟수 **291 → 39 회**,
스텝 med 0.73 → 0.55 px, p95 1.70 → 0.65 px, max 2.51 → 0.79 px.

### 10.3 거리변화(접근·후퇴) 추적 — §6 의 `LFC_SIZE_ALPHA=0` 결정을 번복

**증상.** 박스 크기가 고정이라 search crop 크기(`sqrt(w*h)*4`)도 고정된다.
다가오는 표적은 crop 을 넘어서면 소실되고, 멀어지는 표적은 고정 크기 박스 안에서
작아지며 **템플릿을 배경에 넘겨준다**(점수는 오히려 0.91 로 올라간 채 IoU 0).

**계측 근거.** 배경 고정 + 표적만 스케일 변화하는 합성 시퀀스(패치 합성, 타원 마스크)로
101 프레임 램프를 돌린 결과 (`IoU>=0.5` 프레임 수 / 최종 IoU):

| | 기존 (크기 고정) | 변경 후 |
|---|---|---|
| approach z 1.0→3.0 | 21/101, 0.11 | **101/101, 0.86** |
| recede   z 1.0→0.4 | 50/101, 0.16 | **101/101, 0.88** |

**§6 의 우려(scale pumping)를 어떻게 처리했나.**
크기를 size head 에서 그대로 받으면 회전 시 AABB 가 펌핑한다는 §6 지적은 유효하다.
다만 실측해 보니 전제 두 개가 달랐다.

- **size head 의 스케일 추정은 정확하다.** 100px 박스로 볼 때 hint =
  1.19 / 1.46 / 0.82 / 0.72 (실제 1.2 / 1.5 / 0.8 / 0.6).
- **peak score 는 스케일 판별력이 없다.** crop 0.69x~1.44x 스윕에서 0.883~0.909 로
  평평하고 최대값이 오답 쪽에 있다. → **다중 스케일 탐색(probe) 방식은 폐기했다.**
  penalty·damping 을 넣어 구현·측정까지 해봤으나 정답 부근에서 신호가 없어 동작하지 않는다.

채택한 방식은 size head 를 쓰되 **회전 성분만 저역통과로 거르는 것**이다.
- w,h 를 따로 받지 않고 **기하평균에서 스케일 인자 하나**만 뽑는다(종횡비 불변).
- `LFC_SCALE_LR` 감쇠 + `LFC_SCALE_RATE` 갱신당 변화율 상한.
  회전은 진동성이라 제자리로 돌아오고, 거리변화는 단조라 누적된다.

**잔여 breathing 실측** (2회전, 3°/frame): 정사각 100x100 **5%**, 2:1 장방형 140x70 **12%**.
기하학적 최악(정사각 41%)보다 훨씬 작다 — size head 가 회전에 어느 정도 불변하도록
학습돼 있다. 표적 완전 소실과 맞바꿀 값이라고 판단했다. `LFC_SCALE_LR=0` 이면 원복.

**부수 발견 — 템플릿 EMA 가 스케일 적응을 방해한다.** 템플릿은 박스의
`LFC_TEMPLATE_FACTOR` 배로 crop 하므로, 박스가 작은 채로 EMA 를 돌리면 표적을
작게 재학습해 hint 가 1 로 수렴한다(점수 0.91 인 채 박스가 안 큼). 스케일이
움직이는 동안(`|f-1| > LFC_SCALE_HOLD`) EMA 를 멈추게 했다.
이 한 줄로 approach 최종 IoU 가 **0.54 → 0.86** 으로 올랐다.

**비용 0.** 추가 추론 없음. 실기 갱신율 44.2 Hz(기존) → 44.6 Hz(변경 후).
정지 표적 400 프레임 크기 드리프트 −0%.

> **주의 — 위 44 Hz 는 RTSP 시청자가 없을 때의 값이다.** `RtspServer.push()` 는
> 클라이언트가 붙기 전에는 즉시 리턴하므로 x264 가 아예 안 돈다. GCS 가 붙은
> 실제 운용 조건에서는 **25~27 Hz** 다 (§9 의 23.9 Hz 대비 개선된 값). 변경 전/후를
> 같은 조건에서 비교했으므로 "비용 0" 결론 자체는 유효하지만, **절대 수치를 인용할
> 때는 시청자 유무를 반드시 같이 적을 것.** 이 함정에 한 번 빠졌다.

### 10.4 템플릿 EMA 기본값 0 — §1.6 을 번복

§1.6 에서 "미검증" 으로 남긴 `LFC_TPL_ALPHA=0.15` 를 측정했고, **해가 이득보다 크다.**

EMA 는 박스가 지금 담고 있는 것을 그대로 재학습하므로 작은 정렬 오차가 템플릿에
구워지고 다음 프레임 오차를 키운다(self-reinforcing drift). 표적이 정지해 있어도
박스가 걸어나간다.

정지 장면 drift (600 업데이트 = 45Hz 에서 약 13초):

| | `TPL_ALPHA=0.15` | `=0.0` |
|---|---|---|
| 동일 프레임, 합성 패치 | 2.4 px | 0.6 px |
| 동일 프레임, 실제 텍스처 | **64.3 px**, score 0.92→0.68 | **1.1 px**, score 0.92 |
| 실카메라 40프레임 시퀀스 반복, 강텍스처 | **12.5 px** | **1.2 px** |

부수 효과로 스케일 추종도 좋아졌다 (approach 최종 IoU 0.86 → **0.93**). 템플릿이
고정이라 hint 가 1 로 수렴하지 않기 때문. 회전 breathing 은 정사각 5→3%,
2:1 장방형 12→14% 로 사실상 불변.

**잃는 것**: 표적 외형 변화(면외 회전 등) 대응. 필요해지면 맹목적 EMA 로 되돌리지
말고 **anchor 템플릿**(초기 `z0` 영구 보관 + EMA 가 `z0` 에서 멀어지면 하드 재고정)
으로 갈 것. `LFC_TPL_ALPHA=0.15` 로 언제든 원복 가능.

```

LFC_SCALE_LR=0.40      (0 = 크기 고정 원복. 회전 breathing 이 거슬리면 낮춘다)

LFC_TPL_ALPHA=0.0      (기본값 변경: 0.15 -> 0.0. §10.4)

### 10.6 비행 기록기 — 만들었다가 제거함 (2026-08-21)

프레임 + 프레임별 추적 상태를 같은 `frame_id` 로 남기는 `Recorder` 와 오프라인
`replay.py` 를 만들어 실기 검증까지 했으나 **사용자 요청으로 코드째 제거**했다.
다시 만들 일이 있으면 아래 세 가지를 처음부터 넣을 것 — 전부 실제로 밟은 함정이다.

1. **`json.dumps` 와 numpy 스칼라.** 박스의 `w,h` 는 size head 출력이라
   numpy `float32` 였고, **박스가 움직인 프레임에서만** 직렬화가 터졌다. 빈
   `except` 가 삼켜서 540 프레임 중 250 행이 조용히 사라졌는데 **하필 표적이
   움직인 구간만** 없어졌다 — 진단에 유일하게 필요한 구간이다.
   → `_infer` 가 Python float 만 반환하도록 고쳤고 **이 수정은 남아 있다.**
   `set_track_box` 가 예전부터 `round(float(v), 1)` 로 방어하고 있었던 건 이
   함정을 전에도 밟았다는 뜻이다. 추적기 상태를 JSON 으로 내보낼 때 항상 의심할 것.
2. **예외를 조용히 삼키지 말 것.** 실패 카운터를 `/status` 에 노출했어야 했다.
3. **`_bye` 가 `os._exit(0)`** 이라 종료 시 버퍼가 안 비워진다. 파일을 쓰는 기능을
   붙이면 시그널 핸들러에서 명시적으로 flush 해야 한다.

**측정 조건 함정 (기록기와 무관하게 유효).** 기록을 켜니 갱신율이 44 → 26 Hz 로
떨어진 줄 알았는데 격리해 보니 기록기 탓이 아니었다. §10.3 의 주의 참고 —
`RtspServer.push()` 가 클라이언트 없으면 즉시 리턴하므로 **시청자 없이 잰 44 Hz 와
GCS 붙은 27 Hz 를 비교하고 있었다.** 기록기 실비용은 27.3 → 25.7 Hz 였다.

### 10.7 검증되지 않은 것

- **전부 합성 시퀀스 검증이다.** 실제 3D 접근/후퇴의 원근·자세변화·자기가림 없음.
  회전 테스트도 2D 면내 회전이다(§3 의 FlowTracker 표와 같은 한계).
- 실기 카메라로는 스케일 적응 경로를 태우지 못했다. 실내 고정 초점(무한대)이라
  가까운 표적이 흐리고, 거리를 바꿀 표적을 만들 수 없었다.
- 회전 12% breathing 이 실제 운용(제어 루프·조작자 체감)에 어느 정도 지장인지 미확인.
